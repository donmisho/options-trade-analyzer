## Relevant Context — Do Not Deviate Without Escalation

1. **This story builds a read-only contract that two other tickets already depend on.** OTA-782 (*Config CRUD API for engine tables*) explicitly extends *this* endpoint (`GET /api/v1/config/...`) with its write side, and OTA-660 (*Unify frontend score color thresholds*) will source the 70/50 thresholds from this same endpoint. The response shape you define here is a contract. Pick it deliberately; don't make it awkward to extend with POST/PUT/DELETE later.

2. **The canonical source is the runtime `engine_*` tables, read through the already-deployed loader — not a new SQL path.** OTA-698 (*Config loader over the `engine_*` tables*, Production Deployed) already hydrates `engine_apps`, `engine_rules`, `engine_strategies`, `engine_strategy_rule_junction`, and `engine_lookups` into an in-memory model at startup, scoped by `owner_app_id`, and resolves each strategy into a `RuleSet`. The **preferred** implementation reuses that already-resolved config so there is exactly **one** read path. A second, independent table query in the route is the dual-source problem this story exists to kill — re-introducing it on the backend defeats the point. (App layer may import from `app/insight_engine/`; the engine must never import from the app — keep that direction intact.)

3. **Canonical config moves; presentation stays.** The fields that are *canonical* — strategy thresholds, weights, and verdict bands — move to the backend and must not be hardcoded in `web/src/strategy-configs/` afterward. Purely *presentational* attributes that are not a source of truth (display color tokens, the SP/WG/TR/LT abbreviations and colors per `UI-GUIDANCE.md`, ordering for display) **stay** in the frontend — the strategy-taxonomy rename is a separate future effort and the current abbreviations/colors are presentation, not engine config. Draw this line explicitly in Phase 0 and report it before moving anything.

4. **The 70/50 lives in `engine_strategies.verdict_band_set`** (a JSON column per `insight_engine-schema-ddl.md`). The three score bands (EXECUTE ≥ 70, WAIT 50–69, PASS < 50) are confirmed architecture. This story exposes those band thresholds in the response so OTA-660 can later consume them; it does **not** itself refactor the score-color components — that is OTA-660's job.

5. **Values are not yours to change.** This is plumbing. Do not alter any threshold, weight, or band *value*. The values are whatever the tables currently hold under `owner_app_id='OTA'`. If a value looks wrong, that is a separate ticket — note it, don't fix it here.

6. **Frontend formatting contract** (`UI-GUIDANCE.md`): scores render `##.00` (no `$` prefix), dates `mm-dd-yyyy`. If any config-driven display touches these, honor the tokens. This story shouldn't change rendering, but don't regress it.
