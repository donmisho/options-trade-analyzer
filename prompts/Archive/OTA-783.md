## Relevant Context — Do Not Deviate Without Escalation

Source: `insight_engine.md` §6.6 (startup validation — the loader rejects config if any hold)
The save path must reject any write that would trip these, using the **same** path OTA-699 runs at startup:
- a rule references a named value not in the input catalog
- a junction row references a `rule_id`/`strategy_id` that does not exist
- a junction row does not supply every parameter in the rule's `parameter_schema`
- a gate junction row omits `evaluation_order` or `stop_if_fail`
- a strategy's active scoring criteria do not have junction weights summing to 1.0 (within the documented tolerance)
- a verdict band set is not monotonic
- a condition expression references a named formula not in the registered rule library
- a junction parameter value violates the rule's parameter type or bound
- a named value referenced by a rule has null semantics incompatible with the rule's needs

Source: ticket AC — the six check classes that MUST each have a tested rejection path
weight-sum-to-1.0000; `evaluation_order` uniqueness within `(strategy, phase)`; `formula:<name>` registry membership; `verdict`/`candidate_type`/`phase` membership in their `engine_lookups` domains; junction completeness (every `parameter_schema` param supplied; gate rows carry `evaluation_order` + `stop_if_fail`); `terminal_verdict` (when non-null) membership in the strategy's verdict domain.

Source: `insight_engine.md` §6.6 (enforceability)
- These are not advisory warnings. A save that would prevent clean engine load is rejected. **No partial writes** — the draft/strategy row is written only on success, never left in a non-loadable state.

Source: `insight_engine-schema-ddl.md` §1 (domain validation)
- Discriminator domains (`phase`, `candidate_type`, `verdict`) are validated against their `SHARED` rows in `engine_lookups` at load — never as DB CHECK enums. Save-time validation reads the same lookup domains.

## Scope
Wire save-time validation into the OTA-782 write path by reusing the OTA-699 loader validation. Every config write is validated against the exact rules the engine applies at startup; a write that would fail engine load is rejected at the API with the loader's structured error identity. Writes persist only on success.

## Acceptance criteria
- The API rejects any save that would fail engine startup, returning the same structured error identity the loader produces (not a divergent validator).
- Each of the six ticket check classes has a rejection path exercised by a test.
- A valid save passes and persists; an invalid save persists nothing (no partial/non-loadable state).
