## Relevant Context — Do Not Deviate Without Escalation

**Source: OTA-807 scope.** `business-rules.md` is reshaped into exactly three sections:
1. **Input definitions** — every named value the options adapter produces: how it's computed, data source, tier (RAW / DERIVED / COMPUTED), type, and null semantics. The prose companion to the §5.1 input catalog.
2. **Rule catalog, grouped by common rule type** (earnings, liquidity, cushion, probability, etc.). For each rule: **intent** (plain-language why — e.g. "never enter within 7 days of earnings because of theta acceleration"), **logical evaluation formula** (e.g. `earnings_date - today() > 7`), **required inputs**, and **expected output** (gate pass/fail, score contribution, or adjustment).
3. **Domain semantics** — trading-philosophy decisions that don't fit a single rule (e.g. why PoP uses long-leg delta).

**Source: `insight_engine.md` §9 + migration governing principle.** Rule *content* — thresholds, weights, gate behaviour — lives in the runtime tables; the spreadsheet is a build-time seed only. `business-rules.md` documents what the rules *are and why*, it is not a second source of rule values. Where a value is quoted, mark it as reflecting the seeded junction/config, not as the authority.

**Source: OTA-807 scope (hard boundary).** Strategies are **NOT** documented inline here — they are self-documenting in the Strategies table + junction rationale. If a strategy needs long-form/visual explanation, `business-rules.md` carries a *pointer* to an unstructured doc, never the content.
