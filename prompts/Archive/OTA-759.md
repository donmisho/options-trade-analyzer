## Relevant Context — Do Not Deviate Without Escalation

**Source: `insight_engine.md` §1 — single evaluation path.**
"There is no second evaluation path. Duplicative rule logic across consumers is a design defect, not an acceptable shortcut." After this story, **no `/analyze/*` route filters, scores, or assigns a verdict itself.** A route's only jobs: parse request → resolve strategy id → call adapter → call engine → shape response.

**Source: `insight_engine.md` §5 + §5.2 — adapter contract.**
The route asks the consumer-specific input adapter for candidates; it never fetches market data or computes domain values itself. The engine drives COMPUTED population via callback (`adapter.populate_computed(candidates, needed) -> list[Candidate]`) — the route does not orchestrate tiers.

**Source: `insight_engine.md` §8 — engine boundaries.**
The engine is not responsible for presenting results; the consumer renders the returned result record. The route returns the engine's `ResultRecord`(s); it does not re-shape verdicts or scores.

**Source: `insight_engine.md` §3.8 — verdict bands.**
Verdict bands are per-strategy config, never literals in app code. This route must neither introduce nor retain any `70` / `50` band literal. (The `_assign_verdict` literal removal itself shipped under OTA-760; do not reintroduce it here.)

**Source: ticket OTA-759 — engine call shape.**
`engine.evaluate(candidates, strategy_id, source_app_id="OTA")`. Confirm the exact signature in Phase 0 against the deployed engine runtime (OTA-818) before wiring.

## Scope
Convert each `/analyze/*` endpoint into a thin engine invocation: parse request → resolve strategy id → `adapter.produce_candidates(...)` → `engine.evaluate(candidates, strategy_id, source_app_id="OTA")` → shape the response from the returned `ResultRecord`(s). Remove all inline filter / score / gate / verdict logic from the routes; that behavior now lives in engine config + rule libraries.
