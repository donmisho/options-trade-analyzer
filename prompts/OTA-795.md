## Relevant Context — Do Not Deviate Without Escalation

Source: `insight_engine.md` §1 (one engine, many consumers)
Every evaluation surface is a consumer of the **same** engine: SCREENING, DIRECTIONAL, POSITION_HEALTH — each with its own input adapter, strategies, and verdict bands. There is no second evaluation path. This suite proves the **whole** path composes; it does not re-prove pieces already covered by per-feature unit tests.

Source: OTA-759 (verified engine contract) + `insight_engine.md` §4
Engine entry is **keyword-only**: `evaluate(*, candidates, strategy_key, source_app_id, config, registry=None, adapter=None, sink=None, null_semantics=None) -> list[ResultRecord]`. Entry point is `strategy_key` (not `strategy_id`). Strategy keys are canonical hyphenated post-OTA-841; resolution **fails closed** (unknown key → error, never a default substitution).

Source: OTA-844
Post-seed combined registry == **40** formulas (26 screening + 10 directional + 4 position-health: `exit_level_safety_score`, `pnl_band_score`, `stop_breached_floor`, `warning_breached_cap`). All three surfaces must load.

Source: OTA-795 acceptance criteria + `insight_engine.md` §4.2
Use the **real** engine, real adapters, real rule libraries, and **seeded `engine_*` config** — NOT mocks of the evaluation path. Each consumer's run must assert a complete, well-formed result record (gates, scoring, adjustments, verdict) for **at least one passing and one halted** candidate. The full per-rule trace is mandatory and includes non-stopping gate failures and zero-penalty decisions.

Source: `insight_engine.md` §2.4 (fixed pipeline order)
Pipeline phases run gates → scoring → adjustments → verdict, in that order; within a phase, per-strategy `evaluation_order`. Assertions about a result record must respect this order.
